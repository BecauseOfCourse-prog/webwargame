# Specification 0013: T10 Asset References, Archive and Cleanup

Date: 2026-10-25

Status: Implemented and verified. Task T10 / parent B06. T09–T10 complete the B06 storage foundation; actual catalogs and their upload/selection UI remain T12–T14.

## 1. Problem and intended outcome

Images used by saved content must survive archive and cleanup. T09 also retains pending reservations and orphan files after failures, so operators need a bounded recovery procedure that cannot race an old filesystem writer. Add an internal reference registry, administrator archive/restore operations and manual maintenance with conservative retention. No game/content owner is invented and no public arbitrary-reference creation or deletion API is introduced.

## 2. Lifecycle and reference contract

- Asset gains nullable `archivedAt` and `unreferencedSince`; unused uploads initially have an unreferenced timestamp. `AssetReference` has a restricted asset FK and unique `(ownerKind, ownerId, slot)` binding. Owner kinds distinguish future unit/map/rules content; the future caller must save/verify the actual draft/version owner in the same transaction. Synthetic test owners do not implement those catalogs.
- An internal transaction-taking reference service replaces/releases bindings. A missing, pending or archived target cannot receive a new binding. Repeating an unchanged binding is idempotent. Archive preserves existing references and current authorized byte reads; restore allows new bindings again. The last detach starts a fresh unreferenced retention interval.
- Reference changes, archive and cleanup metadata selection share the existing asset advisory-lock protocol with Read Committed for repository services. A single lock is a simple small-group correctness choice; ordered per-asset locks are a later option only if measured content-write contention warrants their complexity. Database triggers/FK additionally protect ordinary direct writes and maintain reference timestamps; no manually forgeable HTTP owner registry is exposed.
- Existing metadata/content contracts remain compatible. Add protected `GET /api/admin/assets/:id/lifecycle`, `POST /:id/archive` and `POST /:id/restore` responses containing lifecycle state/reference count. Existing session/role/request-marker/Origin/CSRF boundaries apply. Archive/restore additionally recheck current session existence/absolute and idle expiry/ADMIN role inside the transaction after acquiring the asset lock, including idempotent repeats, before reading/updating the asset. Upload uses the same post-lock authority helper.

## 3. Retention and maintenance decisions

Ready images are physically eligible only when archived, unreferenced and seven days past both archive and last detach. Active unused images remain retained until explicitly archived. Archive repeats do not reset its timestamp; restore clears it. Pending reservations and generated-UUID orphan files are eligible after seven days, and only when no writer can still create/grow a file. Unknown names, symlinks and directories are never recursively removed.

Use non-expiring filesystem activity markers and an exclusive maintenance gate in the private root. A writer checks the gate, creates its unique marker, then checks the gate again before any reservation/write. It keeps the marker until filesystem work completes and the client operation settles; a database request with an ambiguous outcome may still finish later, so metadata deletion additionally fences late ready updates. Maintenance creates the gate first and refuses if any writer marker remains; new writers then fail safely until maintenance releases the gate. Startup write probes follow the same protocol. Small validated control files are excluded from image-byte accounting. Crashed-process control files are never age-expired: recovery requires explicit offline verification that the recorded processes/containers have stopped before removing only their exact control files. This operational condition applies before migration from an old API binary that lacks markers too.

Manual `assets:cleanup` defaults to dry-run; `--apply` performs a bounded batch. There is no automatic schedule or new service. Ready and pending metadata are deleted only after rechecking reference/retention in a short transaction, with FK protection; file removal follows confirmed commit. Deleting pending metadata first fences late/ambiguous final ready updates: a pending row must not become readable after its file is removed. A lost/failed commit leaves the file alone. A later unlink failure leaves a counted orphan and is safely retryable. The gate proves no filesystem writer can grow a pending/orphan file; after metadata removal its actual remaining bytes continue to consume quota. Orphans are checked against database rows before deletion. Only generated regular files inside the verified private root can be removed.

Local files plus PostgreSQL keep recurring costs unchanged. Seven-day retention trades some disk use for recovery time; revisit it using real content volume and the eventual host budget. Offline crash-marker recovery favors simple, explicit operator steps over unsafe TTL-based cleanup. Later production tooling may automate process-fenced recovery, but cannot treat a timestamp alone as proof of writer termination. Database/files still require coordinated off-host backups (T37).

## 4. Changed components and operation

Add one migration without editing T09's applied migration, reference/lifecycle services and SQL protections, filesystem activity/maintenance helpers, cleanup service/CLI, shared lifecycle contracts and tests. Preserve the existing Sharp dependency and upload limits. Apply migrations with old APIs stopped; start the updated API only afterward. Reads remain administrator-only until catalog/game visibility rules exist.

## 6. Deferred scope and limits

Catalog owners, immutable content versions and image selection/upload UI remain T12–T14. Cleanup is manual and operator-only, not an administrator browser button. No mandatory paid service, production deployment, automated off-host recovery or player asset access is added. The owner subsequently authorized review, corrections and commit/push; implementation and all mandatory documentation are published together after final checks.
