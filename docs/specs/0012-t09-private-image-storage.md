# Specification 0012: T09 Private Image Storage

Started: 2026-10-24. Updated: 2026-10-25.

Status: Implemented and verified. Task T09 / parent B06. T10 owns references, archival and cleanup; this increment does not close B06.

## 1. Problem and scope

Administrators need bounded persistent image storage before unit, map and illustrated-rules catalogs can be implemented. Store decoded static PNG/JPEG/WebP images outside the web root and metadata in PostgreSQL. Upload, metadata and byte reads are administrator-only until later content-specific permissions exist. No upload UI, public URLs, deletion, reference model, game authorization or deployment is included.

## 2. Resulting interfaces and decisions

- `POST /api/admin/assets`: raw image body with exact supported image Content-Type; existing session/ADMIN, request-marker, Origin and CSRF guards run before reading image bytes. A single bounded upload pipeline accepts at most 10 MiB by default, including chunked requests; no multipart parser or client filename is needed.
- `GET /api/admin/assets/:id`: public-safe metadata; `GET /api/admin/assets/:id/content`: normalized image bytes, private/no-store, nosniff and a generated inline filename. All reads require current administrator authorization and the custom request marker. Future UI must use authorized fetch/blob URLs rather than a direct unauthenticated image element.
- Sharp 0.35.5 performs strict full decoding into pixels and re-encoding, with static PNG/JPEG/WebP signature/container allowlisting, orientation normalization, metadata stripping and sRGB conversion. No resizing or artwork recoloring. PNG and WebP are encoded losslessly; JPEG uses quality 95/4:4:4 with the usual lossy rounding. Reject APNG/animated WebP, corrupt/truncated data, MIME mismatch and other formats. Default limits: 8192 pixels per side, 24,000,000 pixels, 10 MiB encoded input/output. Output may expand and exceed the limit. One upload pipeline per instance bounds memory/work. Body deadline: 20 seconds; native decode and encode each use a 10-second Sharp timeout, which excludes queue waiting and is not a hard total wall-clock request limit. Metadata probing is not claimed to be timed by this native pixel-pipeline limit.
- Persistent configured absolute storage directory, default repository `.local/uploads`, generated UUID-only flat paths, exclusive file creation and symlink/non-regular-file rejection. Files never enter frontend public/build directories. Permissions restrict storage to the service account where supported; Windows needs an appropriate directory ACL.
- Default disk budget: 1 GiB, configurable; filesystem free-space reserve: 64 MiB. Under a short PostgreSQL advisory transaction lock with explicit Read Committed isolation, count actual files plus the unwritten portion of every pending reservation and commit a `ready=false` Asset row for the full normalized byte size. Read Committed makes the capacity query see reservations committed before lock acquisition even if the database defaults to Repeatable Read. Only after that commit, exclusively write/sync the file and mark the row ready. A pending reservation counts as `max(actual file size, reserved byteSize)`; files without rows also count. Both quota/free-space checks include outstanding writes. Filesystem work is outside the transaction: its timeout cannot free capacity while a slow write continues. Failed/uncertain persistence leaves a counted pending reservation/orphan; never delete a possibly committed file. No automatic retry/deduplication is promised. Reads require `ready=true`; pending IDs return 404. POSIX syncs the directory entry before marking ready; Windows lacks directory fsync through this Node API.

Local storage and database metadata fit one host without a recurring service bill. Object storage, a separate processing service and multipart infrastructure add unnecessary administration for the current group. Sharp adds native binaries and requires updates; resource limits need measurement on the eventual host. Shared-database writers must share the same storage root/limits; separate backend hosts are unsupported. A persistent bind mount/volume must survive application/container replacement; backup/restore must coordinate database and files (T37).

## 3. Configuration, data and operations

Validated `UPLOAD_DIRECTORY`, `UPLOAD_MAX_BYTES`, `UPLOAD_MAX_SIDE`, `UPLOAD_MAX_PIXELS`, `UPLOAD_MAX_DISK_BYTES` and `UPLOAD_MIN_FREE_BYTES` are described with defaults/ranges in [README](../../README.md#private-image-storage) and [.env.example](../../.env.example). Defaults do not require editing an existing `.env`. Config errors identify constraints without supplied values. Sharp is the only new direct runtime dependency; its optional platform binaries are locked in pnpm. There is no new service or paid component.

The [migration](../../apps/api/prisma/migrations/20261024000400_private_assets/migration.sql) introduces Asset with uploader foreign key (`ON DELETE RESTRICT`), generated v4 UUID, normalized MIME, byte count, dimensions, SHA-256, timestamp and internal `ready` flag. Database constraints bound metadata to the supported maximum configuration envelope. All later database/asset restores must retain the matched files; T10 must account for both ready references and pending reservations during cleanup. Previous migrations remain unchanged.

No original names, paths or credentials are returned. Missing/broken storage fails startup with sanitized diagnostics; full quota rejects further writes while reads remain available. Errors: 400 `INVALID_IMAGE` / `UPLOAD_ABORTED`, 415 `UNSUPPORTED_IMAGE`, 413 `IMAGE_TOO_LARGE`, 408 `UPLOAD_TIMEOUT`, 429 `ASSET_UPLOAD_BUSY`, 507 `ASSET_STORAGE_FULL`, 503 `ASSET_UNAVAILABLE`, 404 `ASSET_NOT_FOUND`; existing authentication/permission/CSRF codes remain. Exact body size is enforced even for chunked input. Upload connections close after their response so rejected unread bodies cannot keep consuming resources. Metadata/content endpoints emit private/no-store and nosniff; content streams through a verified regular-file handle without loading a full stored image per read. Session/role authority is rechecked at reservation time after processing the body.

## 4. Acceptance and verification

Acceptance conditions: successful static formats, full-decode/mismatch/corruption/animation/bounds rejection, authorization/CSRF before consuming a body, bounded interrupted/chunked uploads, safe paths, quota including pending reservations/orphans/concurrent uploads, sanitized storage/database failures, persisted metadata/content across restart and container replacement, migration repeatability, root checks and documentation links. Actual outcomes and platform limits are recorded in [T09 verification](../verification/t09-private-image-storage.md).

Independent implementation review identified a transaction-timeout race in the initial design that held a database lock during file writing. The final durable-reservation protocol above corrects it. The reviewer rechecked accounting and readiness transitions, and dedicated filesystem/HTTP tests cover no-file/partial-file pending reservations and competing instances. The final implementation does not depend on a transaction staying open during filesystem writes.

Implementation Windows root checks passed 117 cases with one file-symlink privilege skip (118 reported); a fresh frozen Linux installation and the same source on a Linux volume passed all 118, including file symlinks. All 61 initial real HTTP/PostgreSQL cases passed, five main migrations are current/idempotent, and an actual API-container replacement retained authorized metadata/bytes with the same digest. An initial Linux run on Windows-mounted dependencies hit existing startup-test deadlines; this failed run and the successful native-volume correction remain separately recorded. Documentation links, whitespace, private-value scans and disposable-data cleanup passed; see [verification](../verification/t09-private-image-storage.md) for evidence and limits. Initial completion preceded the owner's subsequent request for review, corrections and commit/push.

The owner-requested [Review 0010](../reviews/0010-t09-code-review.md) reproduced a quota-reservation stale-snapshot defect when PostgreSQL defaults to Repeatable Read. The reservation transaction now explicitly requests Read Committed, rather than depending on the server default. The alternative of relying on deployment configuration leaves correctness vulnerable to a later server setting; selecting isolation on this one transaction has no recurring service cost and does not change other operations. A controlled HTTP regression waits for an actual competing advisory lock while keeping the committed file absent. Review also corrected stale README statements about image persistence and migration history. No dependency/schema/migration change was required for these review corrections. Fresh verification and publication evidence is recorded in [the review section](../verification/t09-private-image-storage.md#5-owner-requested-review-and-publication).

After the review correction, fresh root checks passed 117 cases with one Windows file-symlink privilege skip (118 reported), and the complete database suite passed all 62 cases. The new HTTP regression failed before the fix and passed afterward; the focused asset suite passed 18/18. No unresolved review finding remains. Commit/push is explicitly owner-authorized and includes the implementation, correction and mandatory documentation together.
